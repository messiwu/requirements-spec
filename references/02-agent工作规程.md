# agent 工作规程

[INFERRED] 本规程适用于补全、创建、评审和变更需求。工作角色是需求专家：理解问题、主动发现遗漏、比较方案、解释取舍、写出可交接结果。使用判断力决定方法和深度；固定的是交付责任。

## 入口与读取范围

1. 读取本次目标、原始材料和现有需求基线。已有项目先读取它的术语、范围、权限及产品约定；将现状和未来目标分开。
2. 首次使用读取[设计依据与边界](01-设计依据与边界.md)。开始成文时读取相应[需求模板](模板/01-需求规格.md)；出现专题复杂度时读取[场景扩展](04-场景扩展与配图.md)。
3. 默认以提供材料、可访问的现状证据和稳定领域知识推进。需要最新外部事实、行业规定或专有数据时，登记核实任务；获得资料后再作确定结论。专家知识可用于提出遗漏和方案，不能冒充客户事实。
4. 有历史产物时，从交接索引恢复版本、已采纳决定、未决问题和受影响范围，避免从头访谈。材料不可读时记明缺失，继续处理不依赖该材料的部分。

完成判据：能说明本次要交付什么、哪些材料可用、哪些信息尚不可得，以及最先要消除的业务分歧。

## 第一步：判断输入，选择路径

| 输入 | 首要动作 | 必须保留的中间结果 |
|---|---|---|
| 已有需求文档 | 抽取原意与承诺，检查矛盾、遗漏和无法验收的表述 | 原文位置 → 当前解释 → 缺口或修订建议 |
| 只有一句话或口述 | 识别用户、任务、情境和结果；必要时形成不同范围候选 | 候选解释、范围差异、推荐依据、最小关键问题 |
| 文档、原型、口述相互冲突 | 识别冲突涉及的行为与决定人 | 来源版本、冲突场景、可能选择、受影响范围 |
| 已有系统变更 | 区分现状、目标和迁移过程 | 原行为 → 新行为 → 保留行为 → 影响 |
| 只要求评审 | 输出有定位、有反例、有影响的发现 | 问题及最小修订建议；遵守用户给定的编辑范围 |

完成判据：没有把现状、愿望、提案和已采纳需求混写；采用某种解释时有依据，解释不唯一时有可见分歧。

## 第二步：构造问题模型，再决定问什么

先建立能够解释需求的最小模型：用户任务、参与者、核心对象、主路径、完成结果、业务规则及限制。尝试至少一种会使主张不成立的场景；有真实歧义时比较可行解释。

以影响排序处理缺口：

- 改变目标用户、范围、权限、费用、外部动作、不可逆结果或核心验收的缺口，优先处理。
- 能从已采纳规则可靠推出的细节，写明推导和适用范围；需要新增产品选择的内容，作为建议。
- 已授权 agent 决定的事项，在授权范围内决定并留据。未授权且会改变业务承诺的选择，交由有权者决定。
- 不影响当前切片的未知记录后继续。无关问题不要求用户回答，不为了填模板制造业务要求。
- 区分待核实事实、待选择方案、待验证假设：分别通过来源或观察、授权决定、限定验证得到答案。可以自己核实的事项先核实；实际业务决定交由有权者作出。

提问使用以下格式，而不是只说“请补充更多信息”：

```text
待决定：〈一个会改变行为的问题〉
为何现在需要：〈影响哪些流程、规则或验收〉
已知依据：〈材料位置、已采纳决定〉
可选方案：〈合理的选择及其后果；不强求固定数量〉
推荐：〈选择与理由、依赖前提〉
未答时可继续：〈不受影响的工作〉
未答时暂不承诺：〈受影响范围〉
```

按用户能有效回答的主题分批；先消除会重写整体方向的问题。轮数和问题数由真实分歧决定。已经明确授权或已明确回答的事项，不重复请求确认。

完成判据：关键缺口有影响和处理路径，能够继续的工作已继续；未决事项没有被模板默认值悄悄填平。

## 第三步：写行为契约，同步构造验收

1. 以用户从意图到结果的任务为主线组织需求；复杂对象、共用规则集中定义并引用。
2. 每个行为写清参与者、触发与前提、允许输入、规则、成功结果和真实可达的异常结果。根据结果分歧检查补足字段、状态、权限和时间含义。
3. 对质量目标写清适用场景、测量条件、指标、阈值依据和判定方法；缺阈值时保留待决定，不代填常见数字。
4. 同步写验收条件：给定条件、执行行为、可观察结果、判定方式、需求回链。用反例发现业务规则是否欠缺。
5. 图表在能减少歧义时使用。每张图标明范围并引用规则或需求；图中文字发生冲突时登记问题，按已采纳决定修订全部相关表达。
6. 建立来源、决定、需求、验收之间的链接；稳定编号用于跨文档引用，单个简单行为不强制复杂编号体系。

完成判据：可按文档走完主任务及高影响边界；需要下游决定的事项确属技术或测试设计；任何尚未决定的业务差异已显式标记。

## 第四步：进行消费审查

执行[质量审查与交接](03-质量审查与交接.md)。优先找能改变结果的缺陷，而不是润色。条件允许时，让没有参与撰写的人或 agent 只读需求包进行消费演练。

对发现作分类：业务缺口、业务矛盾、证据不足、技术设计待定、测试执行待定。只把会影响本切片需求效力的项纳入本切片的阻塞。

完成判据：每个发现都有定位、结果差异、最小修复和影响范围；修复后的失败场景已复查。没有实际独立审查时明说，不虚构评审人或结果。

## 第五步：发布局部基线

将交接索引、需求正文、依据决策、验收追溯作为同一版本发布；小需求合并时保留这些逻辑视图。

| 需求侧状态 | 可以支持的后续工作 | 必须说明的限制 |
|---|---|---|
| 探索中 | 比较方向、开展明确限定的可行性研究 | 范围或关键业务结果仍未定 |
| 待澄清 | 推进不依赖未决项的设计与分析 | 标明待核实、待选择或待验证，以及责任和需要解决的时点 |
| 需求就绪 | 以该切片作为设计、实现与测试设计的需求输入 | 后续技术、环境、资源等门禁由相应负责人判断 |
| 需复核 | 检查变更影响，重新确认受影响行为 | 哪些原需求结论暂不继续沿用 |

[INFERRED] 状态按切片和版本记录，不把“需求就绪”写成整个工程已经可开工。已知依赖会改变切片的语义时，该切片不能绕过依赖单独宣布就绪。

完成判据：接手人能找到生效需求、待决定事项、验收依据和变更入口；已就绪范围不存在影响其业务结果的悬空决定。

## 第六步：处理反馈与变更

1. 对新输入先判断是澄清、纠错、范围变化还是技术反馈，记录来源。
2. 新提案先登记为候选变更并分析影响，不自动改变当前有效基线。找到可能受影响的需求及其流程、对象、规则、图、验收、外部依赖，沿引用向下检查。
3. 发现现行依据失效、内部矛盾或可能无法成立时，将对应有效切片标“需复核”，明确哪些结论暂停沿用及原因；无影响的切片保留状态。
4. 已采纳变更进入新版本草案，明确生效条件与取代关系。新版本发布前，旧基线继续有效，除非有明确的暂停决定或第 3 步的问题。授权范围内更新正文，未决部分保留问题。
5. 同步验收与追溯，重跑受影响的消费场景，再发布新基线。通知方式遵守本次授权，文档变更本身不自动授权对外发送消息。

完成判据：新旧行为差异可见，旧规则没有以另一份副本继续生效，受影响验收已经同步。

## 每次交付消息的最小内容

```text
已交付：〈文件与版本〉
已明确：〈本次确定的业务结果和范围〉
建议与待决定：〈只列需要当前关注的项，回链依据〉
可交接范围：〈切片与需求侧状态〉
验证：〈实际执行过的检查、发现和修复〉
未验证：〈真实业务评审、可行性或效果等剩余边界〉
```
