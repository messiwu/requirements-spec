# 场景扩展与配图

[INFERRED] 根据业务机制选择分析深度，而不是根据“企业”“消费”“智能体”标签自动加载整套栏目。下表中的问题是发现线索；只有会影响当前交付结果的部分进入需求。

## 按机制扩展

| 实际出现的机制 | 重点追问 | 适合补充的表达 |
|---|---|---|
| 多角色协作、审核或交接 | 谁发起、谁执行、谁决定？转交、拒绝、超时和替岗如何影响任务？ | 角色责任表、泳道流程、权限规则 |
| 多组织或共享数据 | 对象归属谁？跨组织可见边界是什么？移动或成员变化后怎样处理？ | 归属关系、可见范围、权限变化场景 |
| 个人使用、注册、订阅或内容消费 | 首次达到价值的路径是什么？退出、中断、多设备和权限撤回会怎样？ | 关键旅程、身份与权益状态、恢复路径 |
| 支付、计费、额度或权益 | 什么事件生效？重复动作、退款、到期、部分成功如何判定？ | 不变量、账务或权益业务状态、决策表 |
| 审核、内容发布或用户互动 | 谁能看见什么？发布前后差异？删除、申诉、屏蔽影响哪些人？ | 内容生命周期、可见性规则、异常场景 |
| 数据导入导出或批处理 | 部分成功如何呈现？数据时点、重复和冲突如何处理？ | 字段语义、批次结果、恢复策略 |
| 长任务、外部系统协作 | 何时算接受、完成、失败、未知？取消是否仍可能产生外部结果？ | 业务时序、状态转移、核对与恢复规则 |
| 既有产品改动 | 老数据、存量任务和老用户适用哪版规则？切换失败怎么办？ | 现状目标差异、迁移要求、兼容边界 |
| 可访问性、多语言、多地区 | 哪些人群和使用环境在范围内？语言、时区、单位如何影响结果？ | 使用环境与可判定质量条件 |
| 法规、合同或行业特定义务 | 适用主体、范围、版本和证据是什么？谁确认解释？ | 外部约束引用与核实项，避免凭印象写义务 |

## 智能体产品需要额外分清的三类约束

[INFERRED] 智能体产品既可能只有内容生成，也可能实际修改外部世界。应分别表达确定性边界、输出质量和失败恢复，不能用一个“准确率”覆盖全部责任。

| 层面 | 需要决定的事项 | 验收方式 |
|---|---|---|
| 每次均须满足的行为边界 | 可读取什么、能执行什么、授权绑定哪些对象和参数、授权何时失效、是否允许后台继续 | 明确输入下检查越界、重复动作、停止及状态回执 |
| 不确定输出的质量 | 任务类型、代表样本、评价尺度、阈值依据、不可接受输出、评审分歧如何裁决 | 固定评估材料和条件，记录结果分布与失败类型 |
| 单次不满意或失败 | 如何重试、纠正、接管、撤销；结果未知时如何核对；已生效动作如何处理 | 故障与低质量场景的用户可见结果及恢复路径 |

按实际范围追问：

- 输入上下文：可用资料、资料优先级、时效和缺失处理是什么？资料中的文字是否可能被误当成执行指令？
- 自主程度：仅建议、生成草稿、经确认执行、在限定条件下自动执行，各自适用什么动作？
- 确认对象：确认是绑定完整草稿、具体参数，还是一段授权策略？后续变化是否需要重新决定？
- 任务生命周期：等待人工、等待外部结果、暂停、取消、失败和结果未知是否需要区分？
- 成本与等待：预算由谁设定，什么计入，达到上限时用户得到什么？数字没有依据时先留问题。
- 记忆与数据：确实需要跨任务保留哪些内容，谁能查看、改正、清除，何时失效？不因产品包含 agent 就默认增加记忆。
- 质量评价：使用什么代表任务、输入资料和参考答案或评分尺度？同一输入是否重复运行、如何汇总、失败样本是否单独设门槛？根据风险确定。

[COMMON] 用词不同但都满足评价尺度的输出可以同时合格。智能体内容验收通常需要评价依据与容许变化；外部动作是否获得授权、是否重复产生业务结果则需要明确可判定边界。

## 选择什么图

| 表达 | 什么时候值得用 | 回答的问题 | 不能替代什么 |
|---|---|---|---|
| 系统边界图 | 多角色或多外部系统导致范围混乱 | 谁和本产品交互？什么属于外部依赖？ | 对依赖行为与责任的文字说明 |
| 流程图／泳道图 | 路径、分支、角色交接复杂 | 谁在什么时候做什么，如何走向结果？ | 条件、字段校验和异常细节 |
| 状态图 | 对象动作受生命周期约束 | 从何状态经什么条件可到哪里？哪些变化非法？ | 权限、状态转移条件和副作用表 |
| 业务对象关系图 | 归属、基数和对象边界容易混淆 | 一个对象属于谁、关联几个对象？ | 字段定义及数据有效性规则 |
| 决策表 | 多条件组合会改变结果 | 不同组合分别采用哪条规则？冲突谁优先？ | 决策依据与未覆盖组合的处理 |
| 业务时序图 | 有等待、回调、并发或外部动作 | 用户何时收到什么结果，哪些动作可能已生效？ | 内部技术设计；不画假定微服务结构 |
| 线框或交互示意 | 页面关系或操作反馈影响需求理解 | 用户如何完成任务、理解当前状态和下一步？ | 业务规则、真实状态和验收依据 |

[INFERRED] 不设必画图数量。单条规则用一句话更清晰时就不用图。采用 Mermaid 等可维护文本图时，保留源文本；需交给不能渲染的阅读环境时再导出图片并标明版本，图片是派生物。

## 图表交付检查

1. 图的标题说明业务对象、场景或切片；注明关联需求和适用版本。
2. 名称与术语表一致。状态变化能定位触发、条件、动作及可观察结果；无意义的“异常处理”节点应补成真实行为。
3. 图中新增分支必须有已采纳规则或显式未决标记；图不能偷偷决定正文没有决定的行为。
4. 文字与图同时修改、同时检查。二者冲突就是需求缺陷；通过依据与决定裁决，不让读者猜哪一份有效。
5. 在实际阅读环境检查可读性。未检查渲染时，交付说明应写“提供图源，渲染未验证”。
