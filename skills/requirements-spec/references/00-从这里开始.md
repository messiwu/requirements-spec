# 需求文档工作包

[KNOWN] 本文件保存独立文档包的使用方式。当前资料已随 `requirements-spec` 技能安装；通过技能使用时，方法定位与模板读取由技能完成，可以跳过下文的手动放置目录与提供方法路径步骤。

[INFERRED] 版本：0.2。定位：把原始表达整理、质疑、补充并形成可交接的需求基线。适用于人和 agent 共同完成需求工作。本包是可直接试用的方法、模板与示例；尚未经过真实项目对照验证。

## 先看结论

[COMMON] 已有需求可以还原；未表达的业务选择需要提出方案并作出决策。文档无法凭空恢复产品经理没有说过的意图，也不能替代架构设计、详细测试设计与最终业务验收。

[INFERRED] 本包以“下游无需猜测业务结果”为质量目标：保留技术实现空间，把会改变用户结果的分歧显式化。完成标准不是章节齐全，而是范围内的任务、规则、对象、边界与验收能相互对应。

## 立即使用

[INFERRED] 如果你关心“实际应该怎么操作”，先读[实际工作使用手册](06-实际工作使用手册.md)：按已有需求、抽象想法、材料冲突、仅评审或变更选择路径，直接复制对应指令。

1. 将本目录放进你的工作区，保留相对路径。
2. 把原始材料放在单独目录，保留版本、来源和原文定位；只有口述时直接保留消息原文。
3. 将下面的入口指令交给 agent。所有产物另存到本次需求目录，保留模板原件。
4. 先审阅 agent 提出的关键分歧，再审阅被写入基线的业务行为；已有明确授权的决策不重复确认。

```text
请读取《01-设计依据与边界.md》和《02-agent工作规程.md》，按需使用模板及场景扩展，担任本次需求专家。

原始输入：〈粘贴需求，或列出材料路径、版本与可读取范围〉
本次目标：〈补全已有需求 / 从零澄清 / 评审 / 处理变更；不明确时先根据材料判断〉
已知约束与决策权限：〈可为空；为空表示尚未给出，不等于无限授权〉
输出目录：〈本次需求目录〉

先形成输入判断、范围草案、关键缺口与建议路径，再推进不依赖未决问题的部分。
关键问题要说明影响，提供合理选项与推荐依据；问题数量随影响和我的回答能力调整。
区分原始陈述、观察证据、推导与建议；把它们是否已采纳单独记录。
最后按《03-质量审查与交接.md》做消费者审查，列明哪些范围可以用于探索、哪些满足进入实现的需求条件、哪些仍待澄清。
本次只完成需求工作，不扩展到技术方案或代码实现。
```

## 一次需求任务实际交付什么

[INFERRED] 默认交付四种逻辑视图。小需求可以合并成一个文件，保留清楚的标题与编号；复杂项目按业务能力拆分需求规格，共用依据、术语和验收索引。文件数量不作为质量门禁。

```text
本次需求/
├── 00-交接索引.md
├── 01-需求规格.md
├── 02-依据与决策.md
└── 03-验收与追溯.md
```

[INFERRED] 合并条件：同一小型变更、一个主要行为、阅读无需频繁跳转。拆分条件：不同业务能力可独立评审，或同一规则被多个流程复用。拆分后保留统一入口、稳定编号和唯一权威定义；不为架构师、开发、测试各维护一份业务规则副本。

## 什么值得固定，什么留给专家判断

| 固定的交付责任 | 保留的判断空间 |
|---|---|
| 来源可追踪，未决事项可见 | 分析方法、推理深度、备选方案数量 |
| 业务结果可解释，验收可判定 | 章节顺序、文件组织、图的形式 |
| 冲突得到处理，局部就绪不冒充全部就绪 | 是否需要访谈、原型、数据分析或额外专业核实 |
| 已有决定与新增提案分开 | agent 在授权范围内作出具体产品选择 |
| 变更影响和版本明确 | 适合本场景的需求粒度与术语 |

[INFERRED] 建议先在真实任务中试用本包。若输入分流、资料读取和交付检查反复稳定，再把《02-agent工作规程》封装为技能入口，其余文件按条件加载。提示词负责启动，模板负责表达，规程负责工作，审查负责发现问题；任一载体都不等于质量保证。
