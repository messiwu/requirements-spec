# 实际工作使用手册

[KNOWN] 通过已安装的 `requirements-spec` 技能使用时，方法目录由技能定位，模板按任务读取；你只需提供原始需求和已有业务材料。本手册的手动目录准备、方法路径占位符用于未安装技能的独立文档场景，后面的澄清、审查与交接步骤仍适用。

[INFERRED] 推荐用法：你提供业务材料、事实与决策权限，agent 负责理解、发现遗漏、提出方案、组织文档和检查一致性；有权决定的人处理会改变业务承诺的选择。你不需要先手工填写模板，也不需要学完所有文件才能开始。

[KNOWN] 本手册对应工作包 0.2，补充实际操作入口，沿用原有四种需求视图与质量规则。以下路径、指令中的尖括号都是待替换内容，示例目录不是已经创建的项目。

## 1. 第一次使用：只准备三样东西

1. 方法目录：本工作包的可读取位置。
2. 原始输入：现有文档、消息、原型说明或你的一句话。尽量保留原文与来源，不必先整理成专业需求。
3. 产物位置：本次需求存放在哪里。若是只支持聊天的环境，要求分文件标题输出正文，由你保存。

[INFERRED] 建议将可复用方法与具体需求产物分开，防止把模板填坏或把教学示例误当成项目事实。已有项目沿用现有目录；没有约定时可参考：

```text
项目目录/
├── 方法/需求文档工作包/      ← 本包，保存规程与空模板
└── 需求/批量导出/
    ├── 原始材料/            ← 原始文档、消息、原型说明
    └── 产物/                ← agent 生成的本次需求基线
```

[COMMON] 工具能否读取材料取决于当前环境。只有聊天能力时，单独写本机文件路径不能保证模型拿到内容；需要粘贴正文或使用该环境实际支持的附件方式。材料不可读时先处理读取问题，不让 agent 假装读过。

### 共用启动指令

复制一次，替换尖括号，再接上后文对应场景的指令。新会话也重新提供这些路径或材料。

```text
本次请担任需求专家，只完成需求工作。

方法目录：〈工作包实际路径，或已提供的附件名称〉
原始输入：〈材料路径、附件、消息或原始描述〉
现行需求基线：〈有则提供；没有写“无”；效力不清写“未知”〉
输出位置：〈目录；无法写文件时分文件标题输出完整正文〉
我的角色与决策权限：〈知道就写；未知可以留明〉
材料状态：〈已采纳需求、草稿、现状描述等；不清楚写未知〉

读取工作包的入口、设计依据和 agent 工作规程，按需读取模板、审查规程和场景扩展。
先报告已读与不可读的材料，并执行下面的场景任务。
你可以自行组织文档、选择分析方法、发现缺口并提出建议；业务决定按已有授权处理。
继续推进已明确或不依赖未决项的工作；需要我作决定时，说清影响、选择和推荐理由。
```

[INFERRED] 不必为了填写启动信息去猜答案。缺材料、没有决策权和不确定当前版本，本身就是本次需要处理的输入状态。

## 2. 先选入口，不必执行所有场景

| 当前情况 | 选择路径 | 首个应该看到的结果 |
|---|---|---|
| 有产品文档，但担心不完整 | A：诊断并补全 | 原意、缺口、冲突、补充建议分开 |
| 只有一个想法或几句话 | B：澄清任务与范围 | 目标用户、任务结果、候选范围与关键分歧 |
| 文档、原型、会议消息互相打架 | C：对齐多来源材料 | 带来源定位的冲突表和取舍问题 |
| 只想判断别人写的需求是否可用 | D：只评审 | 有反例和影响的缺陷报告，原文件不变 |
| 已有确定需求，现在提出变化 | E：处理变更 | 新旧行为差异、影响范围与候选变更 |

## 3. 场景 A：已有产品文档，准备交给开发

### 你准备什么

提供原文及版本；有原型、现状限制或产品经理补充消息时一起提供。说明你知道的效力，例如“这是已批准范围，细节仍需澄清”或“只是未评审草稿”。不知道则写未知。

### 启动指令后追加

```text
请诊断并补全这份需求，保留原始材料。
先建立“原始请求、承诺和约束 → 当前解释 → 缺口或冲突 → 处理建议”的对应关系。
重点找出会迫使架构、开发或测试猜业务结果的地方。
新增字段、流程、规则和阈值要说明依据，建议与原始要求分开。
随后对已明确部分成文，优先向我提出会改变范围、业务结果或验收的关键问题。
不要把补全变成增加一批未被要求的功能。
```

### 你检查与回复什么

先看主任务是否理解正确、原始要求是否遗漏、哪些细节是 agent 新增建议。不要先逐字润色。按第 8 节回答关键问题；已明确授权的事项让 agent 直接处理，不重复审批。

### 何时进入下一步

当主要任务与范围已明确，能够写出的行为先进入草稿；未决问题标清影响。随后执行第 9 节成文与审查，不要求先把所有未来问题都解决。

## 4. 场景 B：没有产品文档，只有抽象需求

### 你准备什么

提供原话、想到的使用者、一次真实或预期使用情境，以及你已经知道的限制。没有这些补充也可以开始，不要为了显得完整编造材料。

### 启动指令后追加

```text
下面是原始想法，还不是已经确定的需求：
〈粘贴原话〉

请先识别谁在什么情况下，需要得到什么结果，以及目前哪里不清楚。
存在不同业务解释时，比较它们的范围、价值和代价，给出推荐依据。
先帮助我确定一个值得交付的完整任务，再细化流程、对象、字段和验收。
不要仅按我的功能名扩写页面，也不要默认增加平台、组织、权限体系或智能体执行能力。
范围未定时保留候选；已经明确的部分继续整理。
```

### 你检查与回复什么

先选择要解决的任务和期望结果。例如：

```text
采用“客服生成回复草稿”这一范围。
本期由客服手工粘贴邮件；发送仍在现有邮件工具完成。
你可以决定文档结构并提出交互建议。
数据保存、对外承诺和质量阈值还没有决定，请单独标出并说明需要谁提供什么信息。
据此继续细化需求和验收。
```

[KNOWN] 以上是示范回复，不是对任何实际产品的授权。

### 何时进入下一步

当能够说清“谁、何时、做什么、得到什么结果、本期到哪里”为止，进入第 9 节。仍有竞争方向时继续比较，不先填满字段表。可参考[抽象需求示例](示例/02-没有需求文档如何推进.md)。

## 5. 场景 C：材料很多，而且相互冲突

### 你准备什么

将文档、原型、会议记录和补充消息分别标注来源与版本；知道哪些决定已生效就说明。材料更新日期只能说明时间，不自动决定效力。

### 启动指令后追加

```text
这些材料可能互相冲突，请先做对齐。
列出每处会造成不同业务结果的冲突：原文位置、两种解释、结果差异、已有决策依据。
可以据现有明确授权裁决的直接处理并留据；缺少依据的给出推荐并登记待决定。
不要默认最新文件、原型或某位发言者的意见自动优先。
不受冲突影响的部分继续成文。
```

### 你检查与回复什么

优先回答规则效力，而不是泛泛说“以产品经理为准”。例如“采用会议记录里的取消规则，仅适用于新订单；存量订单暂不改变”。如果你无权决定，使用第 8 节的转交方式。

### 何时进入下一步

每项关键冲突被裁决，或已明确阻塞哪些范围。检查正文、图和验收是否一起更新，再进入共用审查。

## 6. 场景 D：只评审，不改写

### 启动指令后追加

```text
本次只评审，不修改原始需求文件。
按工作包的质量审查规程，从架构、开发、测试的消费角度检查这份材料。
每项问题写明位置、具体反例或竞争解释、业务影响、最小补充，以及阻塞的工作。
把业务缺口、证据不足、技术设计待定和测试执行待定分开。
结果写入〈评审报告路径，或直接在聊天输出〉。
不要以篇幅、章节数量或排版好看作为通过依据。
```

### 你接下来做什么

只关注有实际业务影响的问题：确认问题成立、纠正审查者误解，或把问题交给有权者处理。若决定继续补全，再明确发出“根据这些采纳意见修订”的指令，转入路径 A；仅请求评审不自动等于允许改写。

## 7. 场景 E：现行需求已经确定，现在要改

### 你准备什么

提供当前有效版本、新要求，以及已知的实现或上线状态。若有存量用户、历史数据或正在执行的任务，说明它们的存在；具体处理可以待决定。

### 启动指令后追加

```text
当前有效基线：〈版本和路径〉。
新变化：〈原文〉。
变化效力：〈仅是提案／已经采纳，并给出确认依据／尚不明确〉。

先给出原行为与新行为的差异，以及受影响的流程、字段、状态、权限、依赖、图和验收。
说明是否影响存量数据、存量任务和已有用户；不要自行确定迁移政策。
候选提案只进入候选记录，不改变现行基线。
已采纳且信息充分的变更，可在新版本草案中更新，并同步验收与追溯。
明确新版本何时生效、取代什么，以及尚需澄清的部分。
```

### 你检查与回复什么

看三件事：这是否只是澄清原意，是否真的改变业务结果，旧用户或旧数据是否受影响。已明确采纳的内容无需再批准一次；尚未确定的变更只作候选分析。

### 何时进入下一步

变更已经采纳且受影响需求明确后，做对应消费审查并发布新版本。只复核受影响范围；保留旧版本和取代关系。

## 8. 共用操作：如何回答 agent 的问题

[INFERRED] 每轮把回答分成事实、选择、未知和授权，可以减少 agent 将试探意见当成决定的风险。无需使用固定表格，清晰表达即可。

```text
补充事实：〈我实际知道的情况，必要时注明来源〉。
纠正理解：〈你哪里理解错了〉。
采用选择：〈问题编号、采用的方案及适用范围〉。
暂不采用：〈哪些只是讨论或未来候选〉。
仍未知：〈问题编号；谁可能知道；我是否有权决定〉。
允许你自行决定：〈具体事项与限制；没有新增授权可省略〉。
继续推进不受这些未知项影响的工作。
```

### 你也不知道答案

```text
这个问题目前没有答案。
请先区分它需要查事实、做产品选择，还是做验证。
说明获取答案的最短路径、现有选项及影响；推荐方案保持为建议。
继续其他部分，明确它阻塞什么，不要替我把未知写成确定要求。
```

### 你是开发或协调者，没有业务决策权

```text
这些业务选择不在我的决策权限内。
请生成一份可转交给需求负责人的问题单，逐项写影响、选项、推荐和需要的回答。
由我转交；不要替我对外发送消息。
保留目前有效决定，推进其余部分。
```

### agent 问得太散，或一直让你填空

```text
请先用已有材料自行分析和提出方案。
按会改变业务结果的影响排序，把同一主题的问题合并，先处理会改变整体范围的问题。
能够查证的事实先查证；需要我选择的请给出推荐及代价。
```

## 9. 共用操作：成文、检查、修订

### 成文

如果启动任务已经包含补全，agent 可在授权范围内持续成文，无需你额外批准每一份文件。需要主动推进时可发送：

```text
依据原始材料、已经采纳的决定和当前授权，更新本次需求包。
以交接索引、需求规格、依据与决策、验收与追溯四种视图交付。
简单需求可以合并，复杂需求按业务能力拆分，共用规则只维护一处。
同步补充可判定的验收和必要图表；保留未决事项的影响。
完成后自审，并告诉我本轮增加了哪些业务选择、哪些范围达到需求就绪。
```

### 你读什么

| 阅读顺序 | 你要作出的判断 |
|---|---|
| 交接索引 | 本次做什么、哪些能交接、哪里卡住，是否符合你的预期 |
| 需求规格中的主任务与关键异常 | 用户能否完成任务，失败时的结果是否可接受 |
| 新增决定与未决问题 | 有没有未经你或有权者采纳的承诺；是否还需别人回答 |
| 代表验收场景 | 按这个结果交付，你是否会认为满足需求 |

[INFERRED] 字段表、状态表、权限表按实际风险深入阅读；不要求每次逐行审读所有模板栏目。发现“我没说过，但文档写死了”的内容，先查看依据，可能是合理推导，也可能是需要撤回的越权决定。

### 独立消费审查

可以由同事或另一个 agent 完成。让审查者先依据文档工作，不用口头补完文档缺口。无法独立审查时如实标为自审。

```text
请只依据这份需求包及它明确引用的业务资料进行消费审查。
需求包：〈具体版本及路径或附件〉。
方法：〈工作包中的03-质量审查与交接.md〉。

从架构视角找出仍需产品决定的事项；从开发视角走通主路径与高影响异常；
从测试视角给出可判断的预期，并尝试两个都符合字面描述但业务结果不同的解释。
每个问题给位置、反例、影响和最小修复。
不要用你自行补出的规则替原文解围；不需要提前设计整个技术架构。
```

### 将评审交回编写者

```text
这是评审发现：〈报告或路径〉。
请逐项核查，成立的在已有授权内修复，并同步关联规则、图、验收和索引。
需要新增业务决定的先给出具体选择；不成立的说明依据。
复查被修复的场景，给出每项关闭或仍开放的状态，保留文档版本。
```

## 10. 共用操作：交给架构、开发和测试

[INFERRED] 交付对象是本次生成的需求基线及必要来源，不是把整套空模板交给下游让他们重做需求。方法包可供审查参考，实际业务规则以指定版本需求包为准。

### 交接前由你检查

1. 有明确的版本、范围和生效依据。
2. 准备交接的切片没有会改变其业务结果的开放问题；其他范围的未决项仍可保留。
3. 原始请求都有去向，关键行为有可判断的验收。
4. 审查发现已处理，外部依赖与尚未进行的验证已经说明。

### 交给架构师

```text
请基于〈需求包及版本〉中标为需求就绪的〈范围〉开展架构设计。
先读取交接索引，再读取对象、业务规则、流程、质量要求和依赖。
保留业务规则与验收的回链；涉及业务结果的新决定回到需求记录处理。
技术可行性、方案权衡和技术风险在架构产物中说明。
```

### 交给开发

```text
本次需求依据为〈需求包及版本〉，实施范围为〈明确切片〉。
结合已经具备的〈架构与实现约定〉进行后续实施工作。
发现规则矛盾或预期结果缺失时，定位到需求编号并反馈，不凭实现便利改写业务含义。
需求就绪只表示需求输入明确；先按项目流程判断其他实施前提是否具备。
```

### 交给测试

```text
请依据〈需求包及版本〉的验收与追溯、流程、规则和边界设计测试。
补充测试数据、覆盖策略和执行用例，回链需求编号。
需求文档无法判定预期结果时，提出需求缺口；不要把当前实现直接当正确答案。
```

[COMMON] 交接后的架构与测试工作可以暴露新的需求问题。需求基线用于统一依据，不意味着从此不再发生澄清；新发现按路径 E 或已有问题流程处理。

## 11. 共用操作：第二天继续，或换一个会话

```text
继续这项需求工作。
方法目录：〈路径或附件〉。
需求包：〈当前版本与路径或附件〉。
新增信息：〈原文；没有则写无〉。
本轮目标：〈解决某些问题／继续成文／评审／交接〉。

先从交接索引恢复生效范围、已采纳决定和未决事项，不从头访谈。
核对新信息是否改变已有决定；材料缺失时说明缺什么。
沿现有编号与版本继续，保留取代关系，并更新本轮结果。
```

## 12. 企业、消费者、智能体场景怎么调整

[INFERRED] 先按输入状态选择 A 至 E，产品类别只影响追问深度。需要时，在场景指令后追加下面对应的一段；不必换一套流程。

| 实际机制 | 可以追加的指令 |
|---|---|
